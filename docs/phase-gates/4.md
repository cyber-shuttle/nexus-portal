  `ProposalWizard.tsx`; the wire shape (`createProposalPayloadSchema`) is

## Deviations from spec / from the prompt's text

1. **Site conversion rates side panel deferred.** Phase 4 spec §3.2 mentions a
   side panel showing `getEffectiveRate` site rates next to each resource ask.
   The wizard ships without the panel; the resource picker selects from the
   PI's own allocations' resources (which already have rates seeded). The
   "conversion rate" surface is a Phase 7 polish item.
2. **Attachments tab disabled (Phase 7).** The justification step renders a
   disabled file input with a "Phase 7" hint, per the prompt.
3. **Cascade auto-detects two synthetic sub-projects per parent.** Real
   sub-project rollup needs a backend `parent_project_id` column. The wizard
   surfaces `${title} — Sub A/B` placeholders so the cascade UX is exercised
   end-to-end. Doc gap should be added under
   `docs/backend-contracts/proposals.md` once that work begins.
4. **PI scope for the credit-transfer wizard uses `session.user.myPiAllocations`.**
   When a PI has no rows in that claim the wizard renders the empty state.
   Phase 3 already flagged that `myPiAllocations` is hard-coded in the dev
   provider — same gap applies here. Default dev persona has `["alloc-001"]`,
   so the wizard renders the source-pick step with one allocation and the
   destination step is empty until the claim is populated. This is acceptable
   for Phase 4 (the MSW handler still exercises the full path against any
   id-pair the user submits) and reopens as a Phase-3 carry-over (#4) for the
   session bootstrap rewrite.
5. **Researcher persona sees an empty proposals list.** Spec §11 Phase 4
   states "user → empty by default". The container intentionally returns
   `rows: []` rather than firing a query.
