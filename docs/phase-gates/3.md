## Mutations added

`src/features/change-requests/api.ts`:

- `createChangeRequest({ compute_allocation_id, requested_su_amount, requested_status, reason, requester_id }) → POST /compute-allocation-change-requests`
- `updateChangeRequest(id, patch) → PUT /compute-allocation-change-requests/{id}`
- `deleteChangeRequest(id) → DELETE /compute-allocation-change-requests/{id}`
- Hooks: `useCreateChangeRequest`, `useApproveChangeRequest`, `useDenyChangeRequest`, `useUpdateChangeRequest`, `useDeleteChangeRequest`. Each invalidates `changeRequestKeys.all`, `audit` keys for the touched allocation, and `adminKeys.changeRequests`.

`src/features/members/api.ts`:

- `searchUsers(q) → GET /users?q={q}` (portal-only; backend contract gap documented).
- `createMembership(payload) → POST /compute-allocation-memberships`
- `updateMembership(id, patch) → PUT /compute-allocation-memberships/{id}`
- `setMembershipStatus(id, status) → PUT /compute-allocation-memberships/{id}/status`
- `deleteMembership(id) → DELETE /compute-allocation-memberships/{id}`
- `createMembershipOverride / updateMembershipOverride / deleteMembershipOverride` (full overrides CRUD).
- Hooks: `useCreateMembership`, `useUpdateMembership`, `useSetMembershipStatus`, `useDeleteMembership`, `useSearchUsers`, plus the three override hooks. All invalidate `memberKeys.forAllocation(allocId)` (and `memberKeys.overrides(membershipId)` for overrides).

All mutations use the existing `apiFetch` JSON wrapper and surface `ApiError` to callers.

## MSW handlers added

- `change-requests.ts` — POST/PUT/DELETE handlers. Generates new ids via `crypto.randomUUID()`, stamps `timestamp`, and appends a `ComputeAllocationChangeRequestEvent` row on `CREATED` and on every status transition. Mutations persist on `seed` for the lifetime of the MSW worker (per browser context).
- `memberships.ts` — POST/PUT/DELETE for memberships and overrides. `/status` sub-route is registered separately so it doesn't collide with the catch-all `/:id` PUT route.
- `users.ts` — added `GET /users?q=` autocomplete handler (matches name + email, case-insensitive contains).
- `admin.ts` — `/admin/change-requests` now honors `status=<list>` and `limit` so the approver queue can fetch all statuses for the admin view.

## UI

- **Submit change request** — `RequestExtensionDrawer` + `RequestExtensionForm` (RHF + Zod). Three change types: `INCREASE_CREDITS`, `EXTEND_END_DATE`, `OTHER`. Reason is required (min 20 chars). On submit the form posts to the backend shape (`requested_su_amount` = current + delta for credits; reason is prefixed with `[EXTEND_END_DATE → date]` or `[OTHER]` when the type isn't INCREASE_CREDITS so the portal can later read back the intent). Drawer state lives in `AllocationDetailContainer`. The Phase 1 placeholder drawer is gone.
- **Approver queue** at `/change-requests` (was a placeholder). `ChangeRequestsListContainer` (route) composes data per persona:
  - `user` → only own (`useChangeRequestsForUser`).
  - `pi` / `co_pi` → own + change requests on allocations in `session.user.myPiAllocations` or where the user is a member.
  - `allocation_manager` → own + change requests on `session.user.assignedAllocations`.
  - `admin` → all (`useAdminChangeRequests`, status param `PENDING,APPROVED,REJECTED`).
  `ChangeRequestsList` is a pure presentational component: status / change-type / date-range / requester-text filters; CASL-gated Approve/Deny row actions; "View" detail drawer with timeline; bulk approve / bulk deny via confirmation dialog (admin + allocation_manager).
- **Member management** — `MembersTab` now exposes "Add member" (PI + admin only), "Overrides", "Deactivate"/"Activate", and "Remove" actions. Confirm dialog gates all destructive actions. `AddMemberDrawer` uses an autocomplete (`UserSearchCombobox`) that calls `searchUsers` once the query is ≥2 chars; existing members are excluded from the result list. `OverridesDrawer` lists, edits, and removes per-resource overrides; the route layer passes a structural `{id,name}[]` array so the feature stays isolated.
- Toaster mounted globally in `Providers` (richColors, top-right). Used for all mutation outcomes.

## Deviations from spec / from the prompt's text

1. **Backend `ComputeAllocationChangeRequest` shape diverges from the prompt's wording.** The prompt says payload requires `requested_change_type` and `requested_amount`. The actual `pkg/models/allocation.go` model has `requested_su_amount`, `requested_status`, `reason`, `change_status`, `requester_id`, `approver_id`. The portal honors the actual backend; the change type is encoded as a `[EXTEND_END_DATE → …]` / `[OTHER]` prefix on the reason field and `INCREASE_CREDITS` carries the delta into `requested_su_amount` (current + delta). If/when the backend adds a `requested_change_type` enum, drop the prefix dance.
2. **Backend `ComputeAllocationMembership` has no `role` field.** Role surfacing is portal-derived (PI = the project's `project_pi_id`; everyone else is "User"). The prompt asked for inline role-edit dropdowns; that would be a fake feature without backend persistence. Instead the tab exposes the actions that *do* persist: add, deactivate/activate (status), remove, and overrides. Role surfacing remains read-only and the gap is documented in `docs/backend-contracts/memberships.md`.
3. **`useChangeRequestsForUser`** is called even for the `pi` persona — own-requests-first, then merged with allocation-scoped admin rows. This is intentional so a PI can submit a request as themselves and immediately see it (without needing to also be a project-PI on their own allocation).
4. **PI `myPiAllocations` is a session claim, not derived live.** Dev personas hard-code `["alloc-001"]`. A future enhancement is to populate this from a `/users/{id}/projects-as-pi` rollup at sign-in.
5. **`MembersTab` row click removed.** Phase 2 had `onRowClick` on the members table; that triggered nested-interactive a11y violations once row-level action buttons landed. Replaced with an explicit "Details" button.
6. **Re-export shims dropped.** `features/change-requests/schemas.ts` and `features/audit/schemas.ts` are gone; consumers import from `@shared/api/domain` directly.

## Open follow-ups for Phase 4+

1. **Backend role enum.** Until membership grows a server-side role, the portal can only do PI-vs-User derivation. Block any "promote to Co-PI" UX until that lands.
2. **`requested_change_type` column or extension table.** The prefix-on-reason hack works for now but won't scale to filterable, indexable queries. Land a real enum next time the schema changes.
3. **`/users?q=` server endpoint.** Portal autocomplete fakes this in MSW. Land a real endpoint with pagination + a `?source=` filter.
4. **PI scope at session-load.** `session.user.myPiAllocations` is hard-coded in the dev provider. Wire it up from `/users/{id}/projects-as-pi` + `/projects/{id}/compute-allocations` at JWT sign-in.
5. **Optimistic mutations.** Approve/Deny currently waits on server roundtrip + invalidate. For bulk actions on dozens of rows this is sluggish; consider an `onMutate` optimistic patch.
6. **Audit log refetch on mutation.** Currently piggybacks on TanStack invalidation. ### MEDIUM 1 — EXTEND_END_DATE form silently swallows submit

`RequestExtensionForm.tsx`: RHF holds `requested_amount: null` from the INCREASE_CREDITS default; switching to EXTEND_END_DATE conditionally renders the field but doesn't unregister it. Zod schema `requested_amount: z.number().int().positive().optional()` rejects `null` (only `undefined` is accepted by `.optional()`). Validation fails silently because there's no error UI bound to the hidden field.

Fix options:
- `requested_amount: z.number().int().positive().nullable().optional()`, or
- `rhf.unregister('requested_amount')` on change-type switch, or
- Discriminated-union schema on `requested_change_type`.

QA verified via devtools-driven `unregister('requested_amount')` then submit: POST 201, toast, audit log shows event — backend path is correct, only the form glue is wrong.

### MEDIUM 2 — Add-member drawer missing role selector

Spec said "Pick role = User". Drawer only has user autocomplete + end date. Help copy says "Role is derived from the project PI". This is partly correct given the backend `ComputeAllocationMembership` has no `role` column — but spec text and UI are now out of sync. Either keep the auto-derive and update spec, or add an explicit role selector + capture it in the schema gap doc.
